## 1. 设计目标与约束

### 1.1 设计目标

1. 10 天内完成可演示、可测试、可部署的四模块 MVP。
2. 四名成员能在稳定边界内并行开发，减少共享代码和数据库冲突。
3. 前后端以 OpenAPI 契约联调，避免靠聊天消息约定字段。
4. AI 回答具有引用、兜底和反馈闭环，不把大模型输出当作可信数据库。
5. 校内系统暂无真实接口时使用 Mock 适配器，同时保留未来替换入口。
6. 采用单机 Docker Compose 部署，保证答辩环境可以一条命令启动。

### 1.2 已确认约束

| 约束 | 确认设计 |
|---|---|
| 开发方法 | Scrum，一个 10 天 Sprint；每日站会，第 10 天评审和回顾 |
| 业务范围 | M1 AI 知识与对话、M2 校园服务、M3 社区互助、M4 平台治理 |
| 后端语言 | Python 3.12 |
| LLM | 固定 `deepseek-v4-pro`，API Key 由项目方提供 |
| Embedding | 本地 `bge-small-zh-v1.5` |
| 认证 | 内置演示账号 + 密码 + JWT，不对接校园统一认证 |
| 校园系统 | 通过 Mock 适配器返回演示数据 |
| 部署 | Docker Compose 单机演示部署 |
| 上线要求 | 不上线，不承载真实生产数据和自动心理危机通知 |

### 1.3 架构原则

- **模块化单体优先**：业务模块逻辑隔离，但打包为一个 FastAPI 应用；避免四套微服务带来的网关、分布式事务和部署成本。
- **契约优先**：先定义 OpenAPI，再写实现；前端类型和客户端由契约生成。
- **单一数据所有者**：每张业务表只能由所属模块写入，跨模块不得直接更新。
- **外部依赖适配**：DeepSeek、Chroma、文件存储和校内 Mock 均通过 Port/Adapter 隔离。
- **长任务异步化**：文档解析、切分、Embedding 和索引通过 Celery Worker 执行。
- **AI 不参与权限判断**：认证、授权、状态流转、配额和敏感信息过滤由确定性代码完成。
- **先完成 P0**：P1/P2 只能在全部 P0 冒烟测试通过后进入 Sprint。

## 3. 总体架构

### 3.1 架构风格

采用“前后端分离 SPA + 模块化单体 API + 独立异步 Worker + 基础设施容器”的结构。

![逻辑组件与模块边界](assets/overview-logical-components.png)

### 3.2 分层结构

| 层次 | 职责 | 禁止事项 |
|---|---|---|
| 前端展示层 | 页面、路由、状态、表单、SSE 消费、错误展示 | 不拼接 SQL；不自行推断权限；不散落手写 API 类型 |
| API 入口层 | 路由、认证上下文、参数校验、响应封装、异常映射 | 不直接写复杂业务规则 |
| 应用服务层 | 编排用例、事务、权限检查、跨模块接口 | 不依赖具体 HTTP 请求对象 |
| 领域层 | 实体、状态机、业务规则、领域异常 | 不依赖 FastAPI、SQLAlchemy、DeepSeek SDK |
| 基础设施层 | Repository、外部 Gateway、缓存、文件、向量库 | 不把供应商对象暴露到领域层 |

### 3.3 技术组件

| 类别 | 组件 | 说明 |
|---|---|---|
| Web 前端 | Vue 3、TypeScript、Vite | 学生端与管理端共用单页应用 |
| UI 与状态 | Element Plus、Vue Router、Pinia | 模块级路由和 Store |
| API 客户端 | Orval/Axios；聊天流使用 Fetch Stream | 普通接口生成客户端；SSE 需要可携带 Authorization Header |
| 后端 | FastAPI、Pydantic v2、Uvicorn | REST、OpenAPI、文件上传和流式响应 |
| ORM/迁移 | SQLAlchemy 2、Alembic | PostgreSQL 数据访问和版本迁移 |
| 异步任务 | Celery、Redis | 文档入库、索引重建和可选统计任务 |
| 关系数据库 | PostgreSQL | 业务事实、用户、会话、审计和任务状态 |
| 向量库 | Chroma | 每个知识库独立 Collection |
| Embedding | sentence-transformers + bge-small-zh-v1.5 | 后端 Worker 进程内单例加载 |
| LLM | OpenAI Python SDK + DeepSeek V4 Pro | OpenAI 兼容 Chat Completions API |
| 文件 | Docker Volume 本地目录 | 原始上传文件与解析中间产物 |
| 反向代理 | Nginx | Vue 静态资源、`/api` 代理和 SSE 禁用缓冲 |
| 测试 | pytest、HTTPX、Vitest、Playwright | 单元、接口、契约和端到端测试 |

## 4. 四个业务模块

### 4.1 M1 AI 知识与对话

职责：知识库、文档、入库任务、向量检索、RAG 编排、会话、消息、引用和反馈。

核心组件：

- `KnowledgeApplicationService`：知识库和文档用例。
- `IngestionService`：创建任务、保存任务状态、提交 Celery Job。
- `DocumentParserRegistry`：按文件类型选择解析器。
- `TextSplitterPort`：封装递归切分策略，后续可增加语义切分。
- `EmbeddingPort`：封装 `bge-small-zh-v1.5`。
- `VectorStorePort`：封装 Chroma Collection 操作。
- `RetrieverService`：权限过滤、相似度检索、阈值和引用映射。
- `ChatOrchestrator`：上下文构造、Prompt、DeepSeek 流式调用、兜底和持久化。
- `LLMGateway`：DeepSeek API 适配器。

模块公开能力：知识库管理 API、文档与任务 API、对话 API、消息详情 API、反馈 API、内部检索服务。

### 4.2 M2 校园服务中心

职责：办事指南、材料规则、部门联系人、宿舍报修工单、状态流转和评价。

核心组件：

- `ServiceGuideService`：指南查询和适用对象过滤。
- `MaterialChecklistService`：根据校区和学生类型生成材料清单。
- `WorkOrderService`：工单创建、幂等校验、状态机和评价。
- `CampusSystemPort`：校内系统抽象接口。
- `MockCampusSystemAdapter`：读取数据库/JSON 演示数据。

工单状态机：

```text
submitted -> accepted -> processing -> completed
     |           |             |
     +--------> rejected       +-> cancelled（按规则）
     +--------> cancelled
```

状态改变必须由 `WorkOrderService` 校验，不允许 API 层直接赋值。

### 4.3 M3 校园社区与互助

职责：话题、帖子、评论、互动、活动报名、失物/拾物、候选匹配和举报入口。

核心组件：

- `CommunityContentService`：帖子、评论和可见性规则。
- `ReactionService`：点赞、收藏的幂等操作。
- `CampusEventService`：活动容量、报名和取消。
- `LostFoundService`：失物/拾物发布、认领和完成。
- `LostFoundMatcher`：类别、地点、时间和关键词的可解释打分。
- `ModerationPort`：向 M4 提交审核请求并查询审核结果。

MVP 匹配采用确定性加权规则，不在 10 天内训练推荐模型：

```text
score = 类别匹配 35% + 地点匹配 25% + 时间接近 20% + 关键词相似 20%
```

阈值和权重放入配置表；候选结果必须同时返回匹配原因。

### 4.4 M4 平台治理与基础能力

职责：登录、JWT、用户、角色、权限、配置、内容审核、敏感词、审计、基础指标。

核心组件：

- `AuthService`：密码校验、Token 签发、刷新和退出。
- `AuthorizationService`：角色权限和资源范围检查。
- `ModerationService`：敏感词命中、审核状态和处置理由。
- `AuditService`：记录安全和业务关键操作。
- `ConfigService`：读取可公开配置和受保护配置。
- `MetricsQueryService`：聚合四模块基础统计。

M4 只管理身份、审核事实和审计，不直接修改其他模块业务表。审核结果由模块公开接口或应用事件更新内容可见状态。

## 5. 模块依赖规则

### 5.1 允许依赖

| 调用方 | 可调用 | 用途 |
|---|---|---|
| 所有模块 | M4 认证上下文/授权服务 | 获取 `user_id/roles/permissions` |
| M1 | M4 安全检测 | 检查提问和回答内容 |
| M2 | M4 审计服务 | 记录工单敏感操作 |
| M3 | M4 审核服务 | 提交内容审核和举报 |
| M4 | 各模块只读统计接口 | 生成基础看板 |
| M1 Chat | M2/M3 只读工具接口（P1） | 将问答路由到业务查询 |

### 5.2 禁止依赖

- M2、M3 不直接读取 M1 的 Chroma Collection。
- M1、M2、M3 不读取密码哈希、Refresh Token 等认证表。
- M4 不直接更新工单、帖子、活动和知识文档状态。
- 前端模块不得绕过统一 API Client 调用其他模块内部地址。
- Celery 任务不得绕过应用服务直接执行未经校验的跨模块写操作。

### 5.3 模块通信方式

MVP 在同一 Python 进程中优先使用应用服务接口；异步入库使用 Celery Queue。审计通过统一中间件和显式业务事件写入。为控制 10 天复杂度，MVP 不引入 Kafka、RabbitMQ、分布式事务或完整 Outbox。

## 6. 前端概要设计

### 6.1 应用结构

```text
frontend/src/
  app/                  # 路由、布局、权限守卫、全局错误
  api/generated/        # 由 OpenAPI 生成，禁止手改
  api/stream/           # Chat Fetch Stream 客户端
  modules/
    chat-kb/            # M1 页面、组件、store
    services/           # M2
    community/          # M3
    admin/               # M4
  shared/               # 通用组件、类型、格式化、权限指令
```

### 6.2 路由概要

| 路由组 | 主要页面 | 权限 |
|---|---|---|
| `/login` | 登录页 | 匿名 |
| `/chat` | AI 对话、历史会话、引用抽屉 | 学生及以上 |
| `/services` | 指南列表、指南详情、部门联系人 | 学生及以上 |
| `/work-orders` | 本人工单、创建、详情 | 学生；处理页面需处理员权限 |
| `/community` | 话题、帖子详情、活动 | 学生及以上 |
| `/lost-found` | 失物列表、发布、候选匹配 | 学生及以上 |
| `/admin/knowledge` | 知识库、文档、入库任务 | 知识管理员 |
| `/admin/governance` | 用户、角色、审核、审计、看板 | 对应管理权限 |

### 6.3 状态管理

- Pinia 只保存跨页面状态：认证用户、权限集合、全局配置、当前会话摘要。
- 列表和详情数据优先由页面 Query 管理，不把所有服务端数据长期复制到 Store。
- Access Token MVP 可保存在内存；Refresh Token 建议使用 HttpOnly Cookie。若为简化演示采用浏览器存储，必须在文档中标注仅限 Demo，且禁止写入日志。
- 路由守卫只用于用户体验，最终权限必须由后端校验。

### 6.4 流式聊天

浏览器使用 Fetch Stream 或 `@microsoft/fetch-event-source`，原因是原生 `EventSource` 不能方便地携带 Bearer Token。客户端按 `meta/delta/sources/done/error` 事件更新同一条消息，并保存 `request_id/message_id` 用于断线查询。

## 7. 后端概要设计

### 7.1 目录结构

```text
backend/app/
  main.py
  bootstrap/            # 应用创建、生命周期、依赖装配
  common/               # 响应、错误、分页、ID、时间、日志
  modules/
    ai_knowledge/
      api/ application/ domain/ infrastructure/
    campus_service/
      api/ application/ domain/ infrastructure/
    community/
      api/ application/ domain/ infrastructure/
    platform/
      api/ application/ domain/ infrastructure/
  integrations/
    deepseek/ chroma/ storage/ campus_mock/
  worker/               # Celery App 与任务入口
  migrations/           # Alembic
```

### 7.2 请求处理链

```text
Nginx -> RequestIdMiddleware -> CORS/安全头 -> JWT 认证
      -> APIRouter -> Pydantic 校验 -> Application Service
      -> Domain/Repository -> 统一响应或领域异常映射
```

### 7.3 事务边界

- 每个写用例使用一个 SQLAlchemy Session 和一次事务提交。
- Repository 不自行提交事务，由应用服务的 Unit of Work 控制。
- 外部 API 调用原则上不持有长数据库事务。
- Chat 先建立 `pending` 消息并提交，再调用 DeepSeek；结束后更新 `completed/failed`。
- Chroma 写入失败时，入库任务标记失败且文档不进入 `published`，避免半完成数据被检索。

### 7.4 异常体系

领域异常具有稳定 `code`，由全局 Handler 映射 HTTP 状态和通用错误响应。日志保留技术堆栈，客户端只收到安全消息。未知异常统一为 `INTERNAL_ERROR`，不返回数据库、路径或密钥信息。

## 8. 数据架构

### 8.1 数据存储分工

| 存储 | 保存内容 | 一致性要求 |
|---|---|---|
| PostgreSQL | 用户、业务实体、文档元数据、会话、任务、审核、审计 | 业务事实来源，强一致事务 |
| Chroma | Chunk 文本、向量和检索元数据 | 可由 PostgreSQL 文档版本重建 |
| Redis | Celery 队列、短时缓存、限流计数 | 可丢失的派生/临时状态，不作为业务事实 |
| storage volume | 原始文件和可选解析产物 | 数据库保存对象键与哈希，不保存任意本机路径 |

### 8.2 高层实体关系

| 模块 | 聚合根 | 主要关联 |
|---|---|---|
| M1 | KnowledgeBase | 包含 Document；Document 对应 IngestionJob 和多个 Chunk |
| M1 | Conversation | 包含 Message；Message 关联 Citation 与 Feedback |
| M2 | ServiceGuide | 关联 Department 与 MaterialRule |
| M2 | WorkOrder | 包含 WorkOrderEvent；可有一个 WorkOrderRating |
| M3 | Post | 属于 Topic；包含 Comment、Reaction、Report 引用 |
| M3 | CampusEvent | 包含 Registration，用户与活动组合唯一 |
| M3 | LostFoundItem | 关联 LostFoundMatch；匹配指向两条相反类型记录 |
| M4 | User | 通过 UserRole 关联 Role，Role 关联 Permission |
| M4 | ModerationCase | 通过 `target_type/target_id` 引用待审核资源 |
| M4 | AuditLog | 记录 actor、action、resource 和 request_id |

### 8.3 标识与审计字段

- 对外实体 ID 统一 UUID。
- PostgreSQL 时间统一 UTC：`created_at/updated_at/deleted_at`。
- 业务状态使用受控枚举字符串，禁止前端传任意状态。
- 需要并发控制的更新增加 `version` 乐观锁字段或条件更新。
- 逻辑删除数据默认查询自动过滤；审计日志不提供普通删除接口。

### 8.4 Chroma 组织

- 每个知识库使用 Collection：`kb_<uuid_without_dash>`。
- Chunk ID 在 PostgreSQL 与 Chroma 中保持一致。
- Metadata 至少含 `knowledge_base_id/document_id/document_version/source_location/page_number/clean_status`。
- 文档发布后才进入默认检索；停用文档通过 metadata 过滤或重建索引排除。
- PostgreSQL 保存 `embedding_model` 和 `index_version`，避免模型切换后混用不同维度向量。

## 9. AI 与 RAG 架构

### 9.1 入库流水线

```text
上传并校验 -> 保存文件与 Document(pending) -> 创建 IngestionJob
-> Celery 解析 -> 清洗 -> 递归切分 -> bge Embedding
-> 写 Chroma -> 更新统计 -> Document(ready) -> 管理员发布
```

任务阶段：`queued/parsing/cleaning/splitting/embedding/indexing/succeeded/failed`。任务保存进度百分比、当前阶段、错误码、重试次数和时间戳。

### 9.2 RAG 查询流水线

1. 校验用户、会话和可访问知识库。
2. 对输入执行长度限制、敏感词和注入风险基础检测。
3. 读取最近 N 轮对话，形成检索查询；MVP 不做复杂 Agent 规划。
4. 使用同一 `bge-small-zh-v1.5` 生成查询向量。
5. 从授权 Collection 检索 Top-K，按阈值过滤并去重。
6. 无合格结果时直接返回兜底，不调用 DeepSeek 编造答案。
7. 将来源文本、元数据和回答规则组装为 RAG Prompt。
8. 调用 DeepSeek 流式接口，转换为平台 SSE 事件。
9. 保存最终回答、引用、Token 用量、耗时和模型标识。

### 9.3 DeepSeek V4 Pro 适配

固定配置：

```env
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-pro
DEEPSEEK_API_KEY=<runtime-secret>
DEEPSEEK_THINKING=disabled
```

MVP 的校园知识问答以检索事实为核心，为降低首包等待和多轮状态复杂度，默认关闭 Thinking：

```python
client.chat.completions.create(
    model=settings.deepseek_model,
    messages=messages,
    stream=True,
    extra_body={"thinking": {"type": "disabled"}},
)
```

`LLMGateway` 对上层只暴露统一的 `stream_chat()`；API Key 仅存在服务端环境。超时、限流和供应商错误被转换为 `LLM_TIMEOUT/LLM_RATE_LIMITED/LLM_UNAVAILABLE`，并标记是否可重试。

### 9.4 Prompt 约束

- 只根据提供的校园资料回答；资料不足必须明确说不知道。
- 引用编号由后端生成，模型不得伪造来源 URL。
- Prompt 中的数据与指令分区，文档内容视为不可信数据，降低提示注入风险。
- 不在 Prompt 中发送密码、Token、完整联系方式、匿名身份映射和心理倾诉原文。
- 对 Markdown 输出做允许列表清洗，禁止脚本和危险链接协议。

## 10. API 与联调架构

### 10.1 API 分组

| OpenAPI Tag | 所属模块 | 前缀 |
|---|---|---|
| Auth / Users / Roles | M4 | `/api/v1/auth`、`/api/v1/users`、`/api/v1/roles` |
| Knowledge / Documents / Ingestion | M1 | `/api/v1/knowledge-bases`、`/api/v1/documents`、`/api/v1/ingestion-jobs` |
| Conversations / Chat | M1 | `/api/v1/conversations`、`/api/v1/chat` |
| Guides / Departments / WorkOrders | M2 | `/api/v1/service-guides`、`/api/v1/departments`、`/api/v1/work-orders` |
| Topics / Posts / Events / LostFound | M3 | `/api/v1/topics`、`/api/v1/posts`、`/api/v1/events`、`/api/v1/lost-found` |
| Moderation / Audit / Dashboard | M4 | `/api/v1/moderation`、`/api/v1/audit-logs`、`/api/v1/dashboard` |

### 10.2 契约构建流程

```text
编辑 openapi.yaml -> Spectral/Schema 校验 -> Mock Server
-> Orval 生成 TypeScript Client -> 前端开发
-> FastAPI 实现 -> 导出 openapi.json -> CI Diff
```

OpenAPI 是唯一字段真相。前端生成目录禁止手改；SSE 客户端单独维护，但事件 payload Schema 仍在 OpenAPI Components 中定义。

### 10.3 健康检查

- `GET /health/live`：进程存活，不访问外部依赖。
- `GET /health/ready`：检查 PostgreSQL、Redis、Chroma 基础可用性；不强制 DeepSeek 每次探测，避免费用和外部波动。
- 健康接口返回简化结构，不包含密钥、连接串和内部路径。

### 10.4 Mock 适配器契约

`CampusSystemPort` 定义 Python Protocol/ABC；Mock 和未来真实适配器具有同样输入输出模型。通过配置 `CAMPUS_ADAPTER=mock` 注入。Mock 数据放在数据库种子或 `fixtures/`，不得在 Router 中写死。

## 11. 关键业务时序

### 11.1 流式问答时序

```text
前端 -> API：POST /chat/stream（question, conversation_id）
API -> M4：认证与权限
API -> M1：创建 pending Message
M1 -> Chroma：向量检索
Chroma -> M1：Chunks + scores
M1 -> DeepSeek：RAG messages + stream=true
DeepSeek -> M1：文本增量
M1 -> 前端：meta / delta ... / sources / done
M1 -> PostgreSQL：保存回答、引用、usage、completed
```

如果浏览器断开，服务端捕获取消并尽力更新消息状态；客户端通过消息详情查询最终状态，不重复创建相同消息。

### 11.2 文档入库时序

```text
管理员 -> API：上传文件
API -> Storage：保存 UUID 对象键
API -> PostgreSQL：Document + IngestionJob(queued)
API -> Redis：投递 Celery 任务
Worker -> Storage：读取文件
Worker -> Parser/Splitter/Embedding：处理
Worker -> Chroma：写入 Chunk
Worker -> PostgreSQL：Job(succeeded), Document(ready)
管理员 -> API：发布 Document
```

### 11.3 工单状态流转时序

```text
学生 -> API：创建工单 + Idempotency-Key
API -> WorkOrderService：校验字段与重复请求
Service -> PostgreSQL：WorkOrder(submitted) + Event
处理员 -> API：执行 transition(accepted/processing/completed)
Service -> Authorization：检查角色与区域
Service -> Domain StateMachine：检查合法迁移
Service -> PostgreSQL：条件更新 + Event + Audit
```

### 11.4 社区内容审核时序

```text
学生 -> M3：提交帖子
M3 -> M4：敏感词/风险检查
低风险：M3 保存 published
高风险：M3 保存 pending_review；M4 创建 ModerationCase
运营员 -> M4：approve/reject
M4 -> M3 ContentPort：更新可见状态
M4 -> Audit：记录处置人与理由
```

## 12. 安全设计

### 12.1 身份与 Token

- 演示账号由种子脚本创建，禁止开放自助注册。
- 密码使用 Argon2 哈希，不保存明文。
- Access Token 建议 30 分钟；Refresh Token 7 天并在数据库保存哈希和撤销状态。
- JWT 至少含 `sub/jti/roles/iat/exp`，不放密码和敏感资料。
- 登录失败按 IP + 用户名限流，返回统一错误避免账号枚举。

### 12.2 授权

- Router 声明基础权限，如 `knowledge:write`、`work_order:transition`。
- 应用服务再次检查资源级规则，如“只能查看本人工单”。
- 数据库查询必须带资源过滤，不能先查全部再由前端隐藏。
- 匿名内容真实身份反查接口不进入 MVP 演示菜单。

### 12.3 输入与内容安全

- 文件扩展名、MIME、大小和解析异常均校验；存储文件名使用 UUID。
- Markdown 渲染消毒，禁止任意 HTML、`javascript:` URL 和内联事件。
- 社区正文、AI 输入和 AI 输出分别执行内容策略并记录策略版本。
- 心理风险只显示人工渠道，不触发真实人员通知。

### 12.4 密钥管理

`.env` 不提交仓库；只提交 `.env.example`。DeepSeek Key 只注入 API/Worker 容器，不进入前端构建参数。日志和异常对象必须对 `Authorization`、Cookie、数据库 URL、API Key 脱敏。

## 13. 可观测性与运行保障

### 13.1 日志

统一 JSON 日志字段：`timestamp/level/service/module/request_id/user_id/action/resource_id/status/duration_ms/error_code`。用户 ID 可记录内部 UUID，禁止记录密码、Token 和完整敏感正文。

### 13.2 指标

MVP 至少统计：请求数、错误数、P95、Chat 首包/总耗时、DeepSeek Token、入库任务成功率、工单状态数、帖子/举报数。看板读取聚合查询，不直接扫描大体量原始日志。

### 13.3 审计

登录、用户/角色变更、知识发布、工单状态、内容审核、配置修改写入 AuditLog。审计失败时，高风险写操作应回滚或显式告警，不能静默忽略。

### 13.4 备份与重建

演示前备份 PostgreSQL dump、Chroma volume 和上传文件。Chroma 被视为可重建派生数据，但演示前不临时重建。提供 `make seed` 或等价命令恢复稳定演示数据。

### 14.1 容器清单

| 服务 | 端口/卷 | 职责 |

### 14.2 Nginx 关键配置

- `/api/` 反向代理到 `api:8000`。
- 对 `text/event-stream` 关闭代理缓冲和响应压缩缓存。
- 前端 History 路由回退到 `index.html`。
- 限制上传体积并与 FastAPI 配置一致。
- 演示环境使用 localhost；若局域网展示，明确配置 Origin 和 Host。

## 17. 关键架构决策记录（ADR 摘要）

| ADR | 决策 | 原因 | 代价 |
|---|---|---|---|
| ADR-001 | 模块化单体而非微服务 | 10 天、4 人、单机演示 | 不能独立水平扩展每个模块 |
| ADR-002 | PostgreSQL 为业务事实源 | 事务、约束、统一迁移 | 需要规范模块表所有权 |
| ADR-003 | Chroma 保存向量派生数据 | 符合原要求、开发简单 | 需维护索引版本与重建能力 |
| ADR-004 | Celery + Redis 处理入库 | 长任务可重试、有进度 | 增加一个 Worker 和 Redis |
| ADR-005 | 固定 DeepSeek V4 Pro | 用户确认、演示质量优先 | 依赖外网、余额和供应商可用性 |
| ADR-006 | 正常 RAG 关闭 Thinking | 首包更快、上下文处理简单 | 复杂推理能力不作为 MVP 重点 |
| ADR-007 | 校园系统 Mock Adapter | 无真实接口仍可完成联调 | 演示数据不能代表真实生产约束 |
| ADR-008 | OpenAPI 生成前端客户端 | 降低字段漂移 | 契约变更需严格流程 |
